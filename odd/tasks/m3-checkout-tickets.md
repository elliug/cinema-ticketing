# M3 — Checkout, tickets and PDF delivery

Simulated checkout that turns a hold into a paid ticket, with a confirmation
surface where the buyer sees the ticket detail and downloads a PDF carrying the
same detail and a QR, stored in S3 (Floci in development). After M3 the
application must be demonstrable end to end to a real user.
Builds on the integrated M2 reservation core.

## Constraints inherited from the approved architecture

- PostgreSQL stays the source of truth; Redis remains the coordination layer for holds; the ticket is a durable row, not a Redis key.
- The payment boundary and the object-storage boundary are both replaceable adapters, so a real provider later replaces only the adapter (design S8).
- The QR must be verifiable by a later milestone (M4 cashier workflows): the ticket detail it carries has to be checkable server side, never trusted from the client.
- Floci runs as a compose service next to postgres and redis (`floci/floci:latest`, port 4566), and the end-to-end verification of M3 must run against it, exactly as M1/M2 verification runs against compose.

## Decided

These were answered before implementation, so M3 starts with them fixed.

1. **QR content and verification model**: a *signed opaque token*. The server signs the ticket identifier with an HMAC over the ticket, event and seats, and the scan verifies it against the database. The client never carries the full detail, so a photographed QR exposes no personal data, and M4 can distinguish valid, already used and forged tickets.
2. **PDF lifecycle**: generated once when the payment is confirmed, stored in S3 (Floci in development), and served through a short-lived pre-signed URL (`GET /api/v1/tickets/{id}/pdf` → redirect). The stored PDF is an immutable artefact that matches what was sold.
3. **Pricing for v1**: one price per event (`events.price_cents`), so the order amount is price × number of seats. This closes the architecture's open pricing decision for v1 and requires a migration that adds the column to `cinema.events`.
4. **Ticket detail fields**: film, room, date and time, row and seat labels, amount, order reference and the signed QR. One `TicketDetail` projection feeds both the web view and the PDF, so the two cannot drift.
5. **Delivery channel**: download from the web confirmation page only. No email delivery in M3; adding it is a later decision that needs a vendor.

- L5 — T1 delivered the simulated payment boundary in `apps/api/internal/payment`: `Gateway` takes a `Request` (amount in minor units plus a caller supplied provider reference) and returns a `Result` (approved or declined, plus the reference the charge was recorded under). The documented deterministic rule is that an amount whose two least significant minor units equal the sentinel (default `13`) is declined and every other amount is approved, so a test selects the outcome by choosing the amount; `NewSimulatedWithLedger` lets a test pick another sentinel. A declined charge is an outcome with a nil error. Replay state lives in a `MemoryLedger` the caller owns and may share, so two adapter instances agree on a replay; a used reference replays the stored outcome and the same reference with a different amount is `ErrAmountMismatch`. Validation fails closed before any charge is recorded, with distinct errors for a non-positive amount, an amount over `MaxAmountMinorUnits` (1,000,000.00), a blank reference and a reference over `MaxReferenceLength` (200 bytes, the reservation idempotency-key bound), and a zero-value adapter answers `ErrNotConfigured`. The package imports no HTTP client and no credential provider, which is the acceptance item "No real payment credentials or live payment flow exist in v1" held by a test. RED was observed first (the package had no non-test files) and GREEN after the boundary and adapter landed; `-count=3 -race` is green.
- L6 — T3 delivered the checkout service (`apps/api/internal/checkout`) and the public route `POST /api/v1/reservations/{reservationID}/payment`, mounted outside the administrative guard with an `Idempotency-Key` header and **no body**: the amount is `events.price_cents × seats held by the reservation`, computed server side, so there is nothing for a client to send. One checkout is three phases. Phase 1, in one transaction that takes a `FOR UPDATE` row lock on the reservation, requires it to be `held` and inside its window, computes the amount and inserts the `pending` `cinema.payment_attempts` row (client key, request fingerprint, amount, provider), then **commits** — that committed row closes the double-charge window. Phase 2 calls the provider with the amount and the reference `payment_attempt:<attempt id>`, derived from the attempt's own identity (never from the request), so a retry re-sends the same reference. Phase 3, in one transaction, stores the verdict and provider reference on the attempt and, when approved, marks the reservation `paid`, sets the event seats to `sold`, issues one `cinema.tickets` row per held seat (with its `event_id`) and inserts the `cinema.outbox` row, then commits; only **after** that commit is the Redis hold released with the existing compare-and-delete `Release`. A replay with the same key and fingerprint answers from the stored rows (tickets included) and never calls the provider again, even after the reservation is `paid`; the same key with a different fingerprint is `409 idempotency_key_reused`; a `pending` attempt found on retry resumes from the provider call under its own reference instead of creating a second attempt; a stored attempt is never charged another amount (`409 amount_mismatch`). A decline is a **success whose body says so** (`200`, `paymentStatus: "declined"`): the attempt is stored `declined`, the reservation stays `held`, no ticket and no outbox row exist and the Redis hold is kept, because the buyer may still pay inside the window with a new key. Statuses and codes: `400 invalid_input`, `400 not_sellable`, `404 not_found`, `409 hold_expired`, `409 already_paid`, `409 reservation_not_payable`, `409 idempotency_key_reused`, `409 amount_mismatch`, `409 seat_already_sold`, `409 provider_reference_taken`, `503 payment_unavailable` (provider), `503 service_unavailable` (storage); a provider or database transport failure is never a success. The payment adapter decision is now explicit: `payment.NewSimulated()`, the adapter `cmd/api` wires, **never declines** (a real 12,13 EUR ticket is an ordinary purchase), and a decline is a test scenario built with `payment.NewSimulatedWithDeclineRule(sentinel, ledger)`; nothing in `payment.Request` can ask for a decline, because a real provider replaces the adapter and must not inherit simulator knobs. `cmd/api` lists `0003_reservation, 0004_idempotency, 0005_checkout` as the required versions: the checkout store probes `cinema.payment_attempts`, `cinema.tickets`, `cinema.outbox` and `events.price_cents`, and a database without them keeps the reservation surface while logging one line and mounting no payment route. When an attempt approved, the tickets are the durable seat sale (one row per held `event_seat_id`, with `reservation_id` and `event_id`) and the outbox row uses topic `ticket.issued` with payload `{reservationId, eventId, attemptId, amountCents, ticketIds[], seatIds[]}` (the exported `checkout.TicketIssued`), which is what T4 reads its tickets from and what T6/T8 consume to generate and store the PDF. RED was observed first (the package had no non-test files, then the renamed provider constructor and the missing route helpers failed to build, then the first decline fixture failed on the amount it declined) and GREEN after each piece landed; `go test ./apps/api/...` and `go vet ./apps/api/...` are green, and the PostgreSQL evidence is gated on `M3_CHECKOUT_DATABASE_URL` for `make verify-m3` to run.
- L7 — T3 correction round on the uncommitted checkout work, after a reproduced double charge. **Defect 1 (blocker):** one held reservation, two concurrent `Charge` calls with different Idempotency-Keys, two provider calls and one recorded sale — phase 1 only looked the attempt up by its own key, so the second key inserted a second `pending` attempt and both requests reached the provider; phase 3 of the loser then failed on `payment_attempts_captured_per_reservation` and left its attempt `pending` forever while the provider had already taken that money (sale safe, money not). Phase 1 now also refuses a **different** key while another attempt of the same reservation is open: `status = 'pending' AND created_at > now() - interval '2 minutes' AND idempotency_key <> $2`, answered with `ErrPaymentInFlight` → `409 payment_in_flight` ("a payment for this reservation is already being processed; retry with the same Idempotency-Key"), committing nothing. The check sits after `requirePayable` and inside the phase-1 transaction, which is what makes it sufficient: every attempt of a reservation is inserted by a transaction holding that reservation's `FOR UPDATE` lock, so two concurrent checkouts serialize on the lock and the loser reads the winner's committed pending attempt instead of inserting a second one and calling the provider twice. - L8 — T3 closes the residual double charge L7 reported, by moving the guard from a clock to the schema. **What was measured**, with a throwaway database and the L7 code: age one `pending` attempt of a held reservation past `paymentInFlightWindow`, then charge with a fresh key, and the provider is called again — `PROBE first charge error = the payment provider is unavailable: probe: provider transport failure`, `PROBE fresh key after the window = <nil> (PaymentInFlight=false, AlreadyPaid=false)`, `PROBE provider calls for the fresh key = 1`. The concurrent case was already safe (one provider call, the second key answered `409 payment_in_flight`); the hole was the crash window, and a time bound cannot close it. **Why the clock was replaced**: an attempt that dies between the phase 1 commit and the provider call has money with the provider under a reference only that attempt can settle, and no age makes that money stop existing. Two guards that measure the same thing differently are a hazard rather than belt and braces, so `inFlightAttemptQuery`, the `paymentInFlightWindow` constant and the read in `prepareAttempt` are deleted: the authority is now the database. **The invariant now enforced** is `0006_one_open_payment_attempt`: the partial unique index `payment_attempts_open_per_reservation` on `(reservation_id) WHERE status = 'pending'` allows one open payment attempt per reservation, carries a `COMMENT ON INDEX` stating it in domain terms, and is the only guard for the second key. A decided attempt (`captured` or `declined`) leaves the index, so paying again after a decline is still allowed inside the hold, and that is why the reservation and not the client key is the indexed column. `classifyCheckoutError` now names the constraints instead of treating every `23505` as a retry: `payment_attempts_open_per_reservation` is `ErrPaymentInFlight` → `409 payment_in_flight` with no retry, while the reservation-and-key constraint is `errAttemptRaced` so the existing single retry turns a concurrent same-key race into a replay.
